# Add a recipe source

Deliver a working source in the same offline catalog, Explore/favorites filters, weekly planner, recipe details, source badges, and About credits as the existing publishers. Read repository instructions and the relevant sections of `tools/recipe_importer/README.md` before editing. The product name comes from Android `R.string.app_name`; historical Spoon paths and package IDs remain compatibility identifiers.

## Scope and access

Use authorization already supplied by the user; do not ask them to repeat written-consent confirmation. Full downloads require publisher authorization recorded through the crawler's permission flag. Permission for one publisher does not imply authorization for others. A requested source implementation authorizes local code, downloads, validation, and reviewable builds; follow the user's scope for publishing or production Firestore writes.

Check the actual public site, robots.txt, canonical recipe pages, sitemaps, pagination, and any public full-recipe feeds. Prefer complete publisher indexes or feeds. Identify native IDs, Greek locale, recipe URL patterns, image hosts, time units, and stable taxonomy. An HTTP 403 may be an environment/VPN issue: retry normal public access after the user fixes the connection. Do not bypass access challenges or login restrictions. Respect publisher delays, Retry-After, and same-site HTTPS bounds. Run independent publishers in parallel, each with its own rate limiter and resumable checkpoint. Start raw downloads while implementing normalization so slow networking overlaps other work.

## Repository integration

- `tools/recipe_importer/providers.py`: register a stable source key, Greek display name, exact recipe hosts/path regex, native-ID rule, and the verified media hosts/path/query allowlists. Preserve external CDN hosts and necessary tokens such as Drupal `itok`; do not broaden old providers' URL permissions.
- Existing Akis numeric IDs are permanent. New publishers use `recipe_document_id(provider, native_id)`; do not change IDs once favorites, plans, notes, history, shopping entries or share links may reference them. Prefer publisher numeric IDs over mutable titles/slugs.
- Reuse `public_recipe_crawler.py` and add a small `crawl_<source>.py` discovery adapter when appropriate. Existing specialized crawlers remain valid patterns. Store raw evidence and progress durably, retry only failed/pending URLs, and distinguish recipes from nonrecipe posts using actual recipe evidence. Never mark an access/parsing failure as a nonrecipe exclusion.
- `public_recipe_schema.py`: extend the relevant publisher adapter, or add a dedicated schema module if its source structure warrants it. Preserve source payload, grouped ingredients, ordered method steps, photos, canonical links, author, timing, ratings, nutrition, tips, and publication metadata when provided. Do not invent absent fields. Recipe `language` is `el`, not an assumed global locale.
- `full_schema.py`: register the detail schema and independently rederive taxonomy from retained publisher evidence. Category keys must be canonical planner categories; unknown remains `other`. Match ingredient facets through the shared ingredient taxonomy. Keep `ingredient_aliases.json` and Android `IngredientAliases.kt` aligned, and common facet aliases in `facet_aliases.json` / `FacetAliases.kt`; `CommonTaxonomyContractTest` checks both vocabularies. Raw publisher records stay auditable; `normalize_catalog_facets` unifies the offline display and filter projection. Normalize Christmas occasion metadata to `Χριστούγεννα`. The quick filter uses known `totalMinutes` strictly between 0 and 30, including preparation/cooking/waiting; a publisher's quick label or short preparation time alone is insufficient. The offline projection in `timing_guard.py` preserves native artifacts and marks demonstrably contradictory totals unknown. Check mandatory waiting stated in the method against declared timing; contradictory totals must not qualify as quick, and optional overnight suggestions must not be treated as mandatory.
- Export JSONL and a matching manifest with recomputed catalog, summary, detail, payload, and active-ID hashes. Validate with existing full-schema/import contracts and document-size limits. Complete means discovery finished, pending/failed normalization and fetch counts are zero, and all known recipes are accounted for. Report nonrecipe exclusions with evidence. A linked search graph without an exhaustive index cannot certify all of a publisher's recipes.
- `build_local_catalog.py`: include the source artifact deliberately, preserving all existing providers. A partial snapshot must use the explicit partial-artifact path and retain incomplete coverage metadata; never change `complete` to true to satisfy the builder or use a partial source for retirement/production full import. Large ongoing crawls should remain resumable and their counts should be reported accurately.
- Settings source choices: add the publisher to `data/preferences/RecipePublisherOptions.kt` and the `firestore.rules` source allowlist and bounds. `excludedSourceKeys` defaults to empty so existing users include newly added sources automatically. Preserve offline/pending and owner-sync fields; source exclusions intersect Explore filters and new planner picks without removing saved dishes. Test all-selected, mixed selections, all-excluded, reset, and cross-account isolation; run the isolated Firestore rule contract before deploying changed sync rules.
- Android `Recipe.effectiveSourceKey`, `ui/components/PublisherIcon.kt`, `data/preferences/RecipePublisherOptions.kt`: add source identity fallback, official icon mappings, and the publisher website URL. Badge clicks and About credits share that registry; badge taps must open the publisher independently of recipe-card opening or source-chip selection. The discreet recipe attribution link continues to open the original recipe URL. Obtain the actual website favicon/touch icon and keep source/licensing provenance in `docs/source-icons.md`; use local `drawable-nodpi/source_<key>` assets and existing circular badge presentation. Do not redesign or generate replacement publisher logos. Explore source choices/counts are catalog-driven.

## Verification and delivery

Add focused tests for discovery coverage/pagination, native identity/canonical URLs, allowed media URLs, representative real parsing evidence, failed-vs-excluded pages, normalization invariants, and source icons. Exercise resume behavior. Verify at least one real detail from every new source, including its title, photograph, ingredients, method, timing, category, and clickable attribution.

Run the Python importer suite and catalog quality audit. Run Android unit tests and the emulator catalog contract for changes to catalog/taxonomy/filtering; it compares actual SQLite queries against Kotlin filters. Use `connectedDebugAndroidTest` only on a disposable AVD: its automatic uninstall affects the app package across Android users. On an existing multi-user AVD, build with `:app:assembleDebug :app:assembleDebugAndroidTest`, install both APKs with `adb -s <serial> install --user <test-user> -r -t <apk>`, and run `adb -s <serial> shell am instrument --user <test-user> -w -r com.spoon.app.test/androidx.test.runner.AndroidJUnitRunner`. Keep that isolated user active for UI tests; do not add automatic cleanup. If another user must retain the same package's installed APK version, use a disposable AVD because Android shares APK code across users. See `docs/android-device-validation.md` for the complete commands. Build a signed release preserving the signing identity and increase the version code when shipping a changed catalog so installed copies refresh. Deliver the APK via the existing `dist/spoon.apk` procedure and record counts, hashes, validation, and actual limitations in release notes. Do not claim that a downloaded snapshot is all recipes, that uncached remote photos work offline, or that a live site has changed before deployment is verified.
